# 技术尽调检查清单

在把某项技术写入主技术栈前，必须完成以下检查。

## 1. 产品形态匹配

- 该技术是否符合项目最终交付形态？
- 是否解决当前项目的核心使用场景？
- 是否只是因为热门才被推荐？
- 是否存在更简单、更直接的方案？

## 2. 功能覆盖

- 是否覆盖核心功能？
- 是否需要大量二次封装？
- 是否需要自研基础能力？
- 是否能支持后期规划？

## 3. 官方资料

- 是否有官网？
- 是否有官方文档？
- 是否有官方仓库？
- 是否有官方示例？
- 是否有 Release / Changelog？

## 4. 维护状态

- 最近是否仍在更新？
- 最近 Release 是否正常？
- 最近 Commit 是否正常？
- Issue 是否有人回复？
- PR 是否有人合并？
- 是否存在大量无人处理的问题？

## 5. 社区与生态

- 是否有足够用户和案例？
- 是否有插件生态？
- 是否有教程和问题解答？
- 是否被主流云平台、模板、脚手架支持？

## 6. License 与商用风险

- License 是否明确？
- 是否允许商用？
- 是否存在 AGPL、强开源义务或商用限制？
- 是否存在闭源 SDK 绑定？
- 是否存在付费授权边界？
- 是否有第三方依赖 License 风险？

## 7. 部署与成本

- 是否容易部署？
- 是否适合当前预算？
- 是否需要复杂运维？
- 是否需要 Kubernetes、消息队列、缓存集群等额外基础设施？
- 是否适合单人或小团队维护？

## 8. AI 可控性

- 是否有明确目录结构？
- 是否有官方最佳实践？
- AI 是否容易按照统一模式输出？
- 是否容易被 AI 写成拼贴式代码？
- 是否需要额外写开发规范？

## 9. 用户维护能力

- 用户是否能理解？
- 用户是否能部署？
- 用户是否能排查常见问题？
- 后期修改是否依赖高级工程能力？
- 学习成本是否超出当前项目收益？

## 10. 红线检查

以下情况任意命中，不能作为主技术栈：

- License 不清楚；
- 不适合商用；
- 长期无人维护；
- 官方文档严重缺失；
- 与产品形态不匹配；
- 用户无法维护；
- 部署复杂度明显过高；
- 与已有技术栈冲突；
- 会迫使项目过早复杂化；
- 引入后难以替换或迁移。
