# 项目技术栈决策 Skill


## 1. 在完整开发工作流中的位置

- 阶段编号：`02`
- 阶段名称：技术选型 / 技术约束冻结
- 总控入口：[`build-map`](../00-build-map/SKILL.md)
- 本阶段目标：根据产品事实、团队能力、维护成本和官方资料，给出唯一主线技术栈与依赖治理规则。

## 2. 何时启用

- 产品边界已初步明确，需要决定前端/后端/数据库/部署/测试技术。
- 已有技术选择但想评审是否适合长期维护。
- 需要为后续 AI 生成代码设定不可随意变更的技术约束。

## 3. 上游输入契约

本 skill 不应孤立执行。除非用户明确要求单独使用，否则应优先读取或生成以下输入：

- `<project-root>/docs/product/project-brief.md`。
- `<project-root>/docs/product/v1-mvp-scope.md`。
- 目标平台、部署要求、团队能力、预算、是否商用、上线时间。
- 现有技术栈或不可变技术约束。

## 4. 下游输出契约

本 skill 必须把结果沉淀成可被后续 skill 直接消费的交付物：

- `<project-root>/docs/architecture/tech-stack-decision.md`：唯一推荐技术栈与选择理由。
- `<project-root>/docs/architecture/technology-evidence-cards.md`：候选技术证据卡。
- `<project-root>/docs/architecture/dependency-policy.md`：新增依赖申请规则。
- `<project-root>/docs/architecture/banned-technology-list.md`：禁用/慎用技术清单。
- `<project-root>/docs/architecture/stack-reevaluation-triggers.md`：何时允许重评技术栈。

## 6. 本阶段不可违反的硬规则

1. 必须先判断产品形态，再选技术栈。
2. 最终必须给出唯一主线方案；备选只用于解释为什么不选。
3. 不得追新、炫技或默认微服务、Kubernetes、GraphQL、多数据库、复杂 monorepo。
4. 不得混用互斥主栈，如 React 和 Vue 同时作为主前端框架。
5. 技术依据必须可核查；涉及版本、许可、维护状态时应优先查官方资料。
6. 必须输出后续 AI 开发约束，防止擅自换栈和乱加依赖。

## 项目技术选型评审官 Skill

### 一句话定义

项目技术选型评审官用于在写代码之前，根据项目真实信息完成技术路线设计：先判断产品形态，再筛选候选技术，核查官方资料、维护状态和 License，最后输出唯一推荐技术栈，并生成可写入项目文档的技术约束。

### 适用场景

当用户想做一个项目，但还没有确定技术栈、框架、数据库、部署方案、第三方 SDK 或 AI 后续开发规范时，使用本 Skill。

典型输入包括：

- “我要做一个项目，帮我选技术栈。”
- “我想做一个小程序/网站/APP/后台管理系统，用什么技术好？”
- “帮我给这个项目定技术路线。”
- “帮我生成项目技术栈文档，后面让 AI 按这个写代码。”
- “不要直接写代码，先帮我做技术选型。”

### 最高优先级原则

1. 不直接写代码，除非用户明确要求进入编码阶段。
2. 先判断产品形态，再推荐技术栈。
3. 不允许凭空捏造技术选型依据。
4. 技术推荐必须基于项目事实、官方资料、维护状态、License 和后期维护能力。
5. 最终必须给出唯一推荐技术栈，不给用户一堆平级方案制造选择瘫痪。
6. 可以列备选方案，但备选方案只用于解释“为什么不选”。
7. 不追新、不炫技、不默认复杂架构。
8. 不默认推荐微服务、Kubernetes、GraphQL、消息队列、多数据库、复杂 monorepo、服务网格等重型方案。
9. 不推荐冷门、停更、License 不明、文档残缺的技术作为主线。
10. 不混用互斥技术栈，例如 React 和 Vue 同时作为主前端框架。
11. 不绕开成熟框架的官方目录结构和最佳实践。
12. 必须考虑用户自身维护能力和 AI 后续生成代码是否容易保持一致。
13. 必须输出禁用技术清单、新增依赖申请模板、技术栈重评触发条件。
14. 最终结果必须能直接写入 README、项目技术方案或 AI 开发规范。

### 信息不足时的处理方式

不要因为信息不足就停止。

如果项目信息不足，必须先输出：

- 已知信息；
- 缺失信息；
- 本次采用的合理假设；
- 哪些结论依赖这些假设。

然后继续生成初版技术选型报告。所有假设必须明确标注为假设，不能当成事实。

### 必须收集或推断的信息

#### 必填信息

- 项目一句话描述；
- 目标用户；
- 核心功能；
- 产品最终形态；
- 使用场景；
- 预期用户规模；
- 开发者能力；
- 部署要求；
- 是否商用；
- 后期规划。

#### 可选信息

- 是否需要 SEO；
- 是否需要后台管理；
- 是否需要支付；
- 是否需要权限系统；
- 是否需要第三方登录；
- 是否需要文件上传；
- 是否需要 AI 能力；
- 是否需要实时通信；
- 是否需要地图、推送、短信、邮件；
- 是否需要多端同步；
- 是否需要高并发；
- 是否需要私有化部署；
- 是否已有代码或历史技术栈；
- 预算限制；
- 上线时间要求。

### 技术选型执行流程

必须按以下顺序执行：

1. 禁止直接写代码。
2. 读取项目信息。
3. 列出已知信息和缺失信息。
4. 在信息不足时写明合理假设。
5. 判断唯一推荐产品形态。
6. 判断项目复杂度：简单 / 中等 / 复杂 / 商业级 / 高并发级。
7. 识别核心约束：预算、维护能力、部署环境、商用要求、上线时间、团队能力。
8. 从技术候选池中筛选 2 到 4 个候选方案。
9. 核查每个候选方案的官方定位、官方文档、维护状态、License、社区活跃度和部署成本。
10. 用评分表打分。
11. 选出唯一推荐技术栈。
12. 说明其他方案为什么不选。
13. 输出禁用技术清单。
14. 输出新增依赖申请模板。
15. 输出技术栈重评触发条件。
16. 输出可写入项目文档的最终技术栈规范。

### 证据核查规则

对于核心技术，例如前端框架、后端框架、数据库、ORM、云服务、支付 SDK、AI SDK、认证方案，必须核查：

- 官方定位；
- 官方文档完整性；
- 官方仓库或发布页维护状态；
- 最近 Release / Commit / 版本更新情况；
- Issue / PR 活跃度；
- License 类型；
- 是否允许商用；
- 是否存在强开源义务、商用限制、厂商锁定或隐性成本；
- 是否适合用户当前能力；
- 是否适合 AI 后续稳定生成代码。

如果无法联网核查，必须写明：

> 当前未能实时核查该技术的最新维护状态和 License，不能作为最终上线依据。正式上线前需要核查官方文档、官方仓库、包管理平台和 License。

### 产品形态候选池

#### 内容网站 / 营销官网 / 博客 / 文档站

优先候选：

- Astro；
- Next.js；
- Nuxt；
- 静态站点生成方案；
- Markdown / MDX；
- Headless CMS；
- Tailwind CSS。

推荐倾向：

- 内容、SEO、速度优先：优先 Astro。
- 内容 + 登录 + 支付 + 动态业务：优先 Next.js 或 Nuxt。
- 简单官网：不要上复杂后端和微服务。

直接排除：

- 为纯展示页引入大型状态管理；
- 为静态内容站引入复杂后端；
- 为普通官网上 Kubernetes 或微服务；
- 自研 CMS，除非项目明确需要。

#### SaaS Web 应用 / 用户系统 / 支付 / 数据面板

优先候选：

- Next.js + React；
- Nuxt + Vue；
- React + Vite；
- Vue + Vite；
- PostgreSQL；
- Prisma / Drizzle；
- Supabase / Firebase；
- Stripe 或本地支付服务；
- Playwright / Vitest。

推荐倾向：

- 需要 SEO、登录、支付、服务端渲染和 API：优先 Next.js 或 Nuxt。
- 单人 MVP，需要数据库、认证、存储快速上线：可评估 Supabase / Firebase。
- 数据结构清晰、关系型数据明显：优先 PostgreSQL。

直接排除：

- MVP 阶段拆微服务；
- 登录权限全部自研；
- 没有高并发需求就引入 Redis、Kafka、Kubernetes；
- 没有明确数据模型就随意选择 NoSQL。

#### 后台管理系统 / CRM / ERP / 内部工具

优先候选：

- Vue 3 + Vite + Element Plus；
- React + Vite + Ant Design；
- React + MUI；
- NestJS / FastAPI / Django；
- PostgreSQL / MySQL；
- RBAC 权限模型；
- 表格、表单、图表组件；
- 成熟后台模板。

推荐倾向：

- 表格、表单、筛选、权限密集：组件库成熟度优先。
- 国内团队、新手、后台系统：Vue 3 + Element Plus 通常维护成本较低。
- 企业级 React 团队：React + Ant Design 可作为候选。

直接排除：

- 自研表格、日期选择器、复杂表单；
- 同时混用多个 UI 组件库；
- 同时使用 React 和 Vue；
- 为后台系统引入复杂动画框架。

#### 纯后端 API / 移动端后端 / 第三方接口服务

优先候选：

- NestJS；
- FastAPI；
- Django；
- Spring Boot；
- Express；
- Fastify；
- PostgreSQL；
- Redis；
- OpenAPI；
- JWT / Session；
- 日志、监控、错误追踪。

推荐倾向：

- TypeScript、结构化、长期维护：优先 NestJS。
- Python、AI、数据处理、API：优先 FastAPI。
- 需要内置后台、ORM、权限、快速开发完整 Web 系统：优先 Django。
- Java 企业生态、团队已有 Java 经验：优先 Spring Boot。
- 轻量 API、极简服务：Express / Fastify 可作为候选。

直接排除：

- 新手项目默认微服务；
- 无必要时上 GraphQL；
- 没有异步任务需求时引入消息队列；
- 没有性能瓶颈时引入多层缓存；
- 没有团队经验时硬上重型企业框架。

#### 小程序 / 多端应用

优先候选：

- 微信小程序原生开发；
- Taro；
- uni-app；
- 后端 API；
- 云开发 / BaaS；
- 小程序平台 SDK。

推荐倾向：

- 只做微信生态，功能不复杂：优先原生小程序。
- 必须覆盖多个小程序平台、H5 或 RN：评估 Taro。
- 团队偏 Vue 且要多端：评估 uni-app。

直接排除：

- 只有微信小程序却强行上复杂跨端框架；
- 没有多端需求却牺牲平台原生能力；
- 未核查平台审核规则就确定技术方案。

#### 移动 APP

优先候选：

- Flutter；
- React Native；
- Expo；
- 原生 iOS / Android；
- 后端 API；
- 推送、支付、地图、相机、离线存储。

推荐倾向：

- 多平台移动应用、接受 Flutter 生态：评估 Flutter。
- 团队已有 React 经验：评估 React Native / Expo。
- 只是展示信息、低频表单提交：优先考虑 H5 或小程序，而不是 APP。

直接排除：

- 没有原生能力需求就做 APP；
- 单人新手同时做 iOS、Android、Web 三套；
- 没有上架计划就过早投入原生开发。

#### 桌面应用

优先候选：

- Electron；
- Tauri；
- Web 技术栈；
- 本地文件系统；
- 自动更新；
- 安装包构建。

推荐倾向：

- Web 团队，快速做跨平台桌面应用：评估 Electron。
- 追求较小体积、更强系统集成、能接受 Rust 侧能力：评估 Tauri。

直接排除：

- 只是网页功能却强行套桌面壳；
- 没有离线、本地文件、系统托盘、硬件访问需求就做桌面端；
- 新手项目一开始就做复杂自动更新和插件系统。

### 技术评分表

总分 100 分。

- 产品形态匹配度：25 分；
- 功能覆盖度：15 分；
- 成熟度与维护状态：15 分；
- AI 可控性：10 分；
- 用户维护能力匹配度：10 分；
- 部署与成本匹配度：10 分；
- License 与商用风险：10 分；
- 生态与扩展性：5 分。

评分解释：

- 90 - 100：强推荐，可作为主技术栈。
- 80 - 89：可推荐，但需说明风险。
- 70 - 79：只适合作为备选。
- 60 - 69：谨慎使用。
- 60 以下：不推荐。

红线规则：

只要出现以下任意情况，即使分数高，也不能作为主线：

- License 不清楚或不适合商用；
- 最近长期无人维护；
- 官方文档严重缺失；
- 与产品形态明显不匹配；
- 用户完全无法维护；
- 会显著增加部署复杂度；
- 需要大量自研基础设施；
- 与已有技术栈冲突；
- AI 后续容易写出不一致结构；
- 引入后难以替换或迁移。
