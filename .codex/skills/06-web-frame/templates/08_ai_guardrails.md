# AI_GUARDRAILS.md

你是本项目的前端工程执行者，不是自由设计师。所有后续 Vibe Coding 必须遵守本文件。

## 1. 技术红线

1. 不得擅自更换框架、构建工具、UI 组件库、路由方案、状态管理方案、样式系统。
2. 新增依赖必须说明原因、替代方案、影响范围，并等待确认。
3. 不得绕开统一 request client 直接在页面组件中 fetch/axios。
4. 不得把后端核心业务规则写死在前端。

## 2. 目录红线

1. 页面文件只做页面组合，不堆复杂业务逻辑。
2. 业务模块放在 `modules/<domain>/`。
3. 通用组件放在 `components/`。
4. 模块私有组件放在 `modules/<domain>/components/`。
5. API 类型、DTO、错误结构集中管理。
6. 不得随意新建同义目录，例如同时出现 `service/services/api/apis/request/requests`。

## 3. 组件红线

1. 优先复用现有组件和组件库。
2. 同类 UI 结构出现 2 次及以上，必须抽象为组件。
3. 禁止复制粘贴同类表格、筛选栏、弹窗、状态标签、空状态、错误状态。
4. 通用组件不得调用具体业务模块接口。
5. 通用组件不得依赖具体页面路由。

## 4. 样式红线

1. 所有颜色、字号、间距、圆角、阴影必须优先来自 Token 或组件库主题。
2. 禁止在页面中散落硬编码颜色、px、阴影。
3. Tailwind 项目必须使用 theme/token，不得随意写任意值。
4. 组件库主题覆盖必须集中管理并说明原因。

## 5. 页面红线

新增页面前必须先补齐：

- 路由
- 访问角色
- 页面目标
- 核心组件
- 数据字段
- 页面状态：loading / empty / error / success / forbidden / unauthorized
- 响应式规则
- 无障碍要求

## 6. 修改前说明

每次修改前先输出：

```md
本次修改目标：
影响文件：
影响模块：
是否新增依赖：
是否影响路由：
是否影响 Token/主题：
验收方式：
```

## 7. 输出后验收

每次输出代码后必须说明：

- 如何启动。
- 访问哪个路由。
- 如何验证组件复用。
- 如何验证样式 Token 生效。
- 如何验证接口状态。
- 如何运行 type-check/lint/build/test。
